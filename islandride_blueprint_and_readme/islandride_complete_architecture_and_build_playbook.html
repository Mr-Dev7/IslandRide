1. Executive summary

IslandRide is a multi-vendor marketplace, not a single rental-company website. Multiple independent rental businesses can register, get verified, list their bikes and cars, set prices and availability, and receive bookings. Tourists can compare options and book online. The platform owns the discovery, booking, payment orchestration, trust, and administration experience.

Tourists

Search by island, location, dates, vehicle type and price; book; pay; manage pickup, return and reviews.

Rental partners

Register, submit documents, manage fleet/pricing/calendar, approve requests and track earnings.

Platform admins

Verify partners, moderate listings, manage bookings, finance, commissions, disputes and reports.

Recommended starting architecture: one Angular application and one Spring Boot modular monolith, backed by MySQL and Redis. Keep clear module boundaries so services can be separated later if scale justifies it. Do not start with microservices or Kubernetes for the MVP.

3. Main user journeys

Tourist journey

  1. Open destination page and select island/location, pickup/return dates and times.
  2. Filter bikes/cars by category, price, transmission, seating, rating and availability.
  3. Open vehicle details: photos, specifications, partner, pickup instructions, deposit and policies.
  4. Choose instant booking or request partner approval depending on listing rules.
  5. Review backend-calculated price and pay full amount or required advance.
  6. Receive confirmation and booking reference; view booking in dashboard.
  7. Complete identity/licence checks and pickup handover; return vehicle; receive final receipt and review option.

Partner journey

  1. Create account and business profile.
  2. Submit identity/business and vehicle documents for review.
  3. Admin approves the partner and eligible listings.
  4. Add vehicles, photos, specifications, island/location, pricing and booking mode.
  5. Maintain calendar, maintenance blocks and unavailable periods.
  6. Receive instant bookings or approve/reject requests.
  7. Record pickup/return condition, odometer, fuel and damage evidence.
  8. View earnings, commission, refunds and settlement status.

Admin journey

Review partner onboarding → moderate vehicles → oversee bookings → resolve exceptions → manage refunds/commission/settlements → monitor reports and audit logs.

4. High-level system architecture

TOURISTS / PARTNERS / ADMINS | HTTPS / TLS | NGINX / LOAD BALANCER | ANGULAR WEB APPLICATION Public | Tourist | Partner | Admin layouts | REST / JSON | SPRING BOOT APPLICATION +----------------------------------------------------------------+ | Identity | Partner | Geography | Inventory | Pricing | | Availability | Booking | Payment | Commission | Reviews | | Notifications | Support | Admin | Analytics | +----------------------------------------------------------------+ | | | MySQL 8.x Redis Object Storage transactional data cache/holds/rate vehicle photos and limits/idempotency private documents | External integrations: payment gateway, maps/geocoding, email/SMS/WhatsApp, monitoring and error reporting

Architecture style: modular monolith with package-by-feature, explicit interfaces between modules, and clear ownership of data. Keep business rules in the backend. Angular is a client, never the authority for price, availability, payment status or access control.

Why this architecture?

  • Faster and simpler to build, test, deploy and operate with a small team.
  • One transactional boundary helps protect booking and payment consistency.
  • Modules can be extracted later without prematurely adding distributed-system complexity.
  • Redis and object storage handle workloads that should not live in relational tables.

6. Angular frontend architecture

Use one Angular application with role-aware layouts and lazy-loaded features. Keep shared UI components separate from domain-specific features.

Frontend rules

  • Use Reactive Forms and shared validators for complex forms.
  • Use Angular Signals and/or RxJS consistently for state and async data.
  • Use route guards for navigation experience, but enforce all permissions again on the backend.
  • Use HTTP interceptors for correlation IDs and safe auth handling.
  • Lazy-load major feature routes; use responsive accessible components.
  • Never calculate authoritative prices or mark a booking paid in the browser.
  • Use environment configuration for public API URLs; never put secrets in Angular bundles.

Module boundary rule: one module must not directly modify another module's tables through its repositories. Expose an application interface or publish a domain event. Consider Spring Modulith and ArchUnit to verify boundaries.

Engineering principles

  • SOLID: single responsibility, open/closed, substitutability, interface segregation, dependency inversion.
  • DRY, KISS and YAGNI; avoid unnecessary abstraction and premature microservices.
  • Use dependency injection, composition, immutable value objects and explicit transaction boundaries.
  • Use patterns only when useful: Strategy (pricing/payment), Adapter (gateway), State (booking), Repository, Specification (search), Observer/events and Factory.

Data design rules

  • Use UUIDs or non-guessable public IDs where appropriate; an ID is not an authorization check.
  • Store money as DECIMAL, never floating-point types.
  • Store timestamps in UTC; convert to local island time for display and operations.
  • Store media in object storage and only metadata/object keys in MySQL.
  • Use created_at, updated_at, created_by, updated_by and optimistic version fields where appropriate.
  • Use foreign keys, unique constraints, indexes and Flyway migrations.
  • Never store card numbers or CVV. Keep gateway references and transaction metadata only.

9. Availability and booking design

Availability is derived, not a simple boolean

Do not rely on a manually maintained is_available flag. Availability is calculated from vehicle operating status, confirmed bookings, temporary holds, maintenance blocks, buffers, partner policies, pickup/return rules and location constraints.

Booking lifecycle (illustrative)

DRAFT ├─ partner approval required → PENDING_PARTNER_APPROVAL │ ├─ approve → APPROVED → PENDING_PAYMENT │ └─ reject → REJECTED └─ instant booking → PENDING_PAYMENT | payment verified | CONFIRMED | PICKUP_PENDING | ACTIVE | RETURN_PENDING | COMPLETED Other paths: PAYMENT_FAILED | CANCELLED | EXPIRED | DISPUTED

Enforce valid transitions in backend services. Keep booking status history and record actor, timestamp and reason for each transition.

Safe booking algorithm

  1. Receive requested vehicle and pickup/return times.
  2. Validate dates, location, partner policy and vehicle operating status.
  3. Check overlap against confirmed bookings, unexpired holds and maintenance blocks.
  4. Calculate price on the server and create a short-lived inventory hold.
  5. For approval bookings, send the request to the partner and apply a separate approval deadline.
  6. On approval/instant path, create payment order and wait for verified payment result.
  7. Re-check hold validity and booking constraints before confirmation.
  8. Release holds on rejection, cancellation, expiry or failed payment according to policy.
Double-booking prevention is critical. Use database transactions and appropriate row/slot locking or another rigorously tested concurrency strategy, re-check availability before confirmation, and use idempotency keys. A normal unique constraint cannot prevent arbitrary overlapping time intervals. Example: a booking from 10 Nov 09:00 to 12 Nov 09:00 conflicts with a new booking from 11 Nov 10:00 to 12 Nov 10:00.

Illustrative payment hold: 10 minutes, configurable. Partner approval expiry is a separate setting. If payment arrives after the hold expires, revalidate inventory and either safely confirm or start a controlled refund/exception process.

Separate vehicle status from availability

Operating status may be ACTIVE, UNDER_MAINTENANCE, INACTIVE, SUSPENDED or RETIRED. Availability is calculated for a requested time range and should not be stored as a permanent vehicle property.

10. Payments, commissions and finance

Payment flow

  1. Backend calculates the payable amount and creates a gateway order.
  2. Frontend opens the payment gateway checkout.
  3. Gateway sends a signed webhook to the backend.
  4. Backend verifies webhook signature and, where required, fetches payment status from the gateway.
  5. Backend records the payment result idempotently and confirms the booking only after authoritative verification.
  6. Send receipt/notification and update finance records.
A browser redirect or “payment successful” screen is not proof of payment. The backend must verify the gateway result. Protect webhook endpoints against forged requests and replay.

Supported payment options

  • Full payment: customer pays the entire amount online.
  • Partial payment: customer pays a configured advance online and pays the remaining balance at pickup. Record offline collection with amount, method, collector, timestamp and receipt/reference.

Finance records

Track payment orders, attempts, gateway transaction IDs, refunds, commission, partner payable, settlements, reconciliation, deposits and adjustments as separate concepts. Security deposits are liabilities/held amounts, not platform revenue.

Illustrative price breakdown

Rental: 2 days × ₹500₹1,000

Use a provider-independent payment interface so a gateway can be replaced without rewriting booking logic. Keep gateway credentials in a secret manager/environment, never in source control.

11. Security architecture

No system can honestly promise zero vulnerabilities. The goal is to reduce attack surface, enforce least privilege, test security continuously and respond quickly to new issues.

Identity and access

  • Spring Security with short-lived access credentials and rotating refresh tokens.
  • Prefer secure HttpOnly, SameSite cookies for browser refresh/session credentials, with CSRF protection where applicable. Avoid long-lived tokens in localStorage.
  • Hash passwords with Argon2id or properly configured BCrypt; never store plaintext passwords.
  • Use expiring single-use password-reset tokens, verified email/phone flows and throttling.
  • Consider MFA for administrators and sensitive partner actions.
  • RBAC plus resource-level authorization; default deny.

Critical application protections

  • SQL injection: parameterized queries and safe ORM usage.
  • XSS: Angular escaping, safe rendering, Content Security Policy; avoid unsafe HTML.
  • CSRF: secure cookie design and CSRF tokens for state-changing requests.
  • IDOR/BOLA: verify ownership/partner scope on every resource access, not just the route.
  • Brute force and abuse: login/API rate limits, lockout/risk controls and bot protection where needed.
  • Payment: signed webhook verification, idempotency, replay protection and server-side status verification.
  • Uploads: size/type allowlists, content inspection, malware scanning, private storage and signed access links.
  • SSRF: restrict outbound destinations and validate URLs if remote fetch is supported.
  • Audit logs for sensitive admin, partner and financial operations; do not log secrets or sensitive documents.

Infrastructure protections

  • HTTPS everywhere; database and Redis not publicly exposed.
  • Secrets manager, least-privilege service accounts and regular key rotation.
  • Encrypted backups, restore drills, dependency/container scanning and patching.
  • WAF/DDoS protection as appropriate; network segmentation and firewall rules.
  • Define retention/deletion rules for identity, licence and business documents.
Before launch, validate applicable Indian privacy/data-protection, consumer, vehicle rental, insurance, permit, tax and payment obligations with qualified local professionals. Do not assume platform software alone makes a partner or vehicle legally compliant.

14. Business model and pricing

Suggested initial model

  • Free partner registration and basic listing to reduce onboarding friction.
  • Start with an experimentally validated commission, for example 3–5%; 4% is an illustrative starting hypothesis, not a fixed recommendation.
  • Tourist browsing is free; avoid adding a booking fee at MVP launch unless user research supports it.
  • Later options: featured listings, optional partner subscriptions, sponsored destination placements and commissions on additional services.

Pricing engine

Calculate all prices on the backend. Support hourly/daily rates, duration, seasonal pricing, discounts, delivery/pickup charges, taxes, deposits, cancellation fees and partner-specific rules. Store a price snapshot on each booking so later rate changes do not rewrite history.

Hosting principles

  • Deploy Angular static assets to a CDN/static host or serve behind Nginx.
  • Run Spring Boot on a managed application host, VM or container platform.
  • Use managed MySQL/Redis where budget allows; otherwise operate carefully with backups and monitoring.
  • Use private object storage for photos/documents, with signed URLs and access checks.
  • Do not expose MySQL or Redis directly to the public internet.
  • Use Docker Compose for local development and a straightforward production deployment initially. Kubernetes is not required for launch.

Environments

Local → Development → Test/CI → Staging → Production. Keep separate databases, credentials, gateway keys and storage buckets. Test production-like migrations and backups in staging.

Must-test scenarios

  • Two customers attempt to book the same vehicle/time concurrently.
  • Customer closes browser after successful gateway payment.
  • Duplicate webhook arrives; payment and booking are not duplicated.
  • Payment fails or arrives after the hold expires.
  • Partner rejects an approval request.
  • Maintenance block overlaps a requested rental.
  • Customer A attempts to view Customer B's booking.
  • Partner A attempts to access Partner B's vehicle or settlement.
  • Cancellation/refund follows the correct policy and ledger.
  • Offline balance at pickup is recorded with a traceable receipt.

CI pipeline

On each pull request: format/lint → compile/build → unit tests → integration tests → Angular build/tests → dependency/security scan → Docker build. Deploy to staging after merge; production deployment requires approval and a rollback plan.

17. Monitoring, reliability and operations

  • Capture structured logs with request/correlation IDs; never log passwords, tokens, payment secrets or sensitive document contents.
  • Monitor API latency, error rates, database connections, Redis health, booking conversion, vehicle utilization, cancellations, payment success and notification failures.
  • Use OpenTelemetry, Prometheus and Grafana, with alerts for actionable incidents.
  • Health/readiness checks, graceful shutdown, retry with backoff and dead-letter handling for asynchronous failures.
  • Use idempotency for payment, booking and webhook operations.
  • Consider a transactional outbox when database changes must reliably publish events/notifications.
  • Automate backups and periodically prove that restoration works. Define recovery time and recovery point objectives.
  • Maintain runbooks for payment outage, database failure, accidental double booking and data exposure.

18. Andaman-specific product rules

  • Model island and pickup/return location as first-class data, not free-text labels.
  • Example initial destinations: Sri Vijaya Puram (Port Blair), Swaraj Dweep (Havelock) and Shaheed Dweep (Neil Island). Keep these configurable in the database.
  • Do not assume a vehicle can move between islands. Partner policy must define operating island, pickup/return points, permitted transfer, extra charges and return restrictions.
  • Capture driving licence and vehicle documents only when needed, protect them as sensitive data and define retention.
  • Support pickup/return handover evidence: photos, odometer, fuel level, existing damage and customer/partner acknowledgement.
  • Validate applicable local permits, insurance, vehicle rules and rental requirements with local authorities or a qualified advisor.
  • Plan for seasonal demand, ferry/logistics constraints and island-specific operating hours.
  • Build trust through verified partners, verified-booking reviews, transparent deposits, cancellation rules and support contacts.

Phase 4 — Authentication and authorization

Implement authentication and access control only.

Features:
- Tourist and partner registration/login.
- Admin accounts provisioned securely; do not allow public admin registration.
- Email/phone verification integration points.
- Password hashing using Argon2id or correctly configured BCrypt.
- Secure access/refresh session design, rotation, expiry, logout and revocation.
- Password reset using expiring single-use tokens.
- Role-based and resource-level authorization.
- Rate limits for login, registration, reset and sensitive endpoints.
- CSRF protection if browser authentication uses cookies.
- Audit important security events.

Phase 7 — Availability and booking engine

Implement the availability and booking engine. This is a high-risk domain: design and test concurrency before calling it complete.

Availability must combine:
- Vehicle operational status.
- Confirmed booking intervals.
- Unexpired temporary holds.
- Maintenance/unavailability blocks.
- Pickup/return buffers.
- Partner policies and operating island/location restrictions.

Implement both:
A. Instant booking.
B. Partner-approval booking.

Create a backend-enforced booking state machine, status history, cancellation policy, approval deadline, payment deadline and expiry handling. Use transaction boundaries, row/slot locking or another justified concurrency strategy, second availability checks and idempotency keys. Do not rely on a simple unique constraint for overlapping date ranges.

Tests must simulate two concurrent customers attempting the same vehicle/time, duplicate requests, expired holds, partner rejection, maintenance overlap, cancellation and late payment. Explain the locking strategy and demonstrate that only one conflicting booking can be confirmed.

22. Definition of done

A feature is not complete merely because its screen exists. Mark it done only when:
  • Requirements and acceptance criteria are met.
  • Backend validation and authorization are implemented.
  • Database migrations are reviewed and tested.
  • Frontend loading, success, empty and error states work.
  • Unit and integration tests cover business rules and failure paths.
  • API documentation and user-facing help are updated.
  • Logs/audit events are appropriate and contain no secrets.
  • Accessibility and responsive behavior are checked.
  • Security and ownership tests pass.
  • Build, tests and deployment checks actually pass in CI.

24. Additional architecture recommendations

The blueprint already includes the core architecture recommendations. This section makes the important choices more explicit so the team can use them as default engineering decisions during implementation.

1. Launch as a modular monolith

One Spring Boot deployable with strict module boundaries. Avoid microservices, Kubernetes, Kafka and complex service meshes until measurable scale or team ownership requires them.

2. Keep the backend authoritative

Only the backend decides price, availability, commission, booking state, permissions and payment status. The browser displays results; it does not make trusted decisions.

3. Treat booking as the highest-risk module

Design interval conflicts, holds, expiry, concurrent requests, partner approval and late payment before polishing screens. Build concurrency tests early.

4. Use a financial ledger mindset

Keep rental amount, tax, deposit, advance, pickup balance, gateway fee, commission, partner payable, refund and settlement separately traceable. Never overwrite financial history.

5. Make partner onboarding trustworthy

Use a review queue, explicit verification states, rejection reasons, document expiry and audit history. Do not publish unapproved partner listings by default.

6. Build location rules into the domain

Every vehicle must have an operating location/island and pickup/return rules. Do not assume a vehicle can be transferred between islands or returned at a different island.

7. Use private media storage

Vehicle gallery images may be public through controlled delivery; identity, licence and business documents must be private, access-checked and short-lived through signed URLs.

8. Add transactional reliability

Use idempotency for booking/payment actions and consider a transactional outbox for notifications and integration events. A successful database transaction should not silently lose its required event.

9. Keep a booking price snapshot

Save the itemized price, applied rules, tax configuration and policy version used when the booking was created. Later price edits must not rewrite old bookings.

10. Separate deposits from revenue

Track security deposits as held/refundable amounts with their own collection, deduction and return workflow. Do not count them as platform commission or rental income.

11. Design admin permissions narrowly

Separate operations, support and finance permissions. Require stronger authentication and audit logging for refunds, settlements, role changes and sensitive document access.

12. Start with a pilot

Launch with a small number of verified partners and a limited set of islands/locations. Validate booking operations, handover, refunds and partner settlement before broad marketing.

Practical technical defaults

  • API: version under /api/v1; publish OpenAPI and generate/validate frontend API types where practical.
  • Database: MySQL is the source of truth. Use transactions and constraints; use Redis only for cache/ephemeral coordination, never as the only record of a booking or payment.
  • Search: start with indexed MySQL filters and pagination. Add a dedicated search engine only when real search volume or relevance needs justify it.
  • Frontend: one Angular app with route-level lazy loading and shared design tokens. Do not split into micro-frontends for the MVP.
  • Authentication: for a first-party browser app, prefer secure HttpOnly, SameSite cookies with CSRF protection for state-changing requests; finalize the design based on deployment topology and any future mobile clients.
  • Payments: use gateway sandbox first, verify webhooks server-side, reconcile gateway records and never trust browser callbacks.
  • Files: use object storage with upload limits, MIME/content validation, malware scanning where available and private access for sensitive documents.
  • Dates: store UTC instants, retain the relevant destination time-zone identifier, and test daylight/time-zone and pickup/return boundary cases.
  • Deployment: use managed database and object storage if budget allows; automate backups and test restoration before public launch.
  • Versions: choose supported stable Angular, Java LTS and Spring Boot versions at project kickoff; pin versions and document upgrade policy rather than hardcoding an outdated version.

Suggested delivery gates

  1. Gate A — Product approval: SRS, role matrix, cancellation/approval rules, payment policy and island operations approved.
  2. Gate B — Technical foundation: repo, CI, migrations, authentication approach, module boundaries and staging environment work.
  3. Gate C — Booking correctness: conflict/concurrency tests pass and booking lifecycle is auditable.
  4. Gate D — Financial correctness: verified gateway callbacks, refunds, partial balance and reconciliation are tested.
  5. Gate E — Pilot readiness: security review, legal validation, restore test, support runbooks and partner UAT are complete.
Important: These are engineering recommendations, not legal advice. Confirm applicable vehicle rental rules, permits, insurance, consumer obligations, taxation, privacy and payment requirements for the actual operating model before launch.
